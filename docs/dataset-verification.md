# 数据集生成与验证记录

> 口径勘误：下文第 5 节的数值来自旧版统计，保留用于追溯，不可直接与 evidence-v3 指标对比。
> 旧版误将 18 道隔离题归入 answerable、Recall@1 实际检查所有候选，且多源证据要求落在同一切片。
> 修正后的定义及新基线见 evals/README.md 和 docs/retrieval-baseline-corrected.md。


更新时间：2026-10-13（Asia/Shanghai）。本文记录 `evals/` 下星桥科技合成数据集的生成方式、可执行的校验证据、
以及一次真实端到端评估的结果与已知局限。所有数字都来自本机真实执行输出，未做修饰。

> **声明**：语料为合成内容（虚构企业「星桥科技」），不对应任何真实企业制度、产品或人员。
> 下述指标只代表在该合成语料上的表现，**不能**作为真实企业准确率或生产能力的依据。

## 1. 为什么重新做数据集

上一版数据集（已归档到 `evals/legacy/`）只有 6 份文档、2238 字符，指标全部满分：

```
source_recall_at_3: 1.0    refusal_accuracy: 1.0    citation_source_match_rate: 1.0
```

满分的原因不是系统强，而是**题目太容易**：语料每份只有一段 200–400 字，提问措辞与原文几乎一致，
检索没有失败空间。这类数据无法回答"系统在什么情况下会失败"，也就无法支撑简历或面试中的技术讨论。

因此新数据集的验收标准不是"数据量更大"，而是**能稳定复现出真实失败**。

## 3. 标注如何保证可信

题集不是手写 JSON，而是由 `evals/facts/*.jsonl` 通过 `evals/tools/build_questions.py` 装配，
每条标注都要通过机械校验，任一失败即非零退出：

1. `expected_sources` 的文件必须真实存在；
2. `terms`（原文片段）必须**逐字**出现在源文件中——这是"答案确实出自该文档"的证据；
3. 题量、kind 与难度分布必须匹配约定；
4. answerable 的 `reference_answer` 非空；refusal 的 `expected_sources` 必须为空；
5. **提问不得复述原文**：提问与源文的最长公共子串 > 15 字符即失败（防"抄原文"导致指标虚高）；
6. **跨库隔离题必须真的隔离**：若提问库里存在与答案同主题的文档（按文件名主题词判定），
   该题会被拒绝，除非显式写明 `overlap_note` 说明为何不影响评测。

当前 `questions.json` 与 `manifest.json` 由该脚本生成，`tests/test_evaluation.py` 会对
哈希与逐条 terms 再做一次独立回归校验（`23 passed`）。

## 4. 格式保真：PDF 与页码溯源

`evals/tools/build_pdfs.py` 生成 6 份多页文本型 PDF（每库 2 份），用途是验证 PDF 解析与
`chunks.page` 溯源。真实入库后：

```json
"it-vpn-lockout-policy.pdf": {"chunks": 3, "pages": [1, 1, 2], "has_page_numbers": true, "max_page": 2}
```

即同一 PDF 的不同切片分别带上真实页码 1 与 2，检索结果可以回答"这句话在第几页"。

已知限制：这些 PDF 正文为 ASCII——项目环境没有 reportlab/fpdf/fontTools，而内置标准字体不含
CJK 字形，嵌入中文字体又会显著增大仓库体积。因此**不能**据此声称已验证中文 PDF 版式解析。

## 5. 真实端到端评估结果

运行命令与规模：

```bash
python scripts/evaluate_v2.py --run-label synthetic-v1
# 126 份文档上传 1.4s；入库+索引 82.2s；452 个切片；168 题全部成功返回
```

| 指标 | 数值 |
|---|---|
| 成功请求 | **168 / 168** |
| source_recall_at_3（文档级） | **0.7941** |
| chunk_recall_at_3（切片级，top_k=3） | **0.6078** |
| mrr_at_3 | **0.4363** |
| ndcg_at_3 | **0.4791** |
| refusal_accuracy | **0.9792** |
| answerable_response_rate | 0.8417 |
| citation_source_match_rate | 0.4706 |
| keyword_pass_rate（仅参考） | 0.3627 |
| 检索耗时 p50 / p95 | 450.6 ms / 917.98 ms |
| 问答总耗时 p50 / p95 | 1753.45 ms / 4016.11 ms |

按难度拆分（有答案题）：

| 难度 | 题数 | 文档召回 | 切片召回 | MRR |
|---|---|---|---|---|
| easy | 24 | 0.9167 | 0.75 | 0.5278 |
| paraphrase | 30 | 0.8667 | 0.6667 | 0.4889 |
| numeric | 30 | 0.8667 | 0.7333 | 0.5055 |
| **multi_source** | 18 | **0.3889** | **0.1111** | **0.1111** |

### 结论一：数据集确实产生了分化

同一套系统在 easy 题上文档召回 0.92，在 multi_source 题上掉到 0.39，切片级更是掉到 0.11。
这正是上一版数据集无法暴露的信息，也是"优化前后可对比"的前提。

### 结论二：multi_source 失败的直接原因是 top_k 太小 —— 并已用对照实验验证

`top_k=3` 时每题只能取回 3 个切片，而多源题需要两份文档都进前 3。逐题核对可见典型模式：

```
HR-32 期望 [新员工试用期管理与转正流程.md, 绩效考核管理办法.md]
      实得 [新员工试用期管理与转正流程.md ×3]      ← 第二份文档完全没有进榜
IT-31 期望 [扫描到邮箱与共享盘操作指南.md, 企业邮箱容量与附件限制说明.md]
      实得 [扫描到邮箱与共享盘操作指南.md ×3]
```

这说明它是**检索深度问题**，而不是"两份文档都不相关"。为验证这一点，在**同一套语料、同一套题、
同一模型配置**下只改 `top_k` 重跑了一次（`--reuse --top-k 5`）：

| 指标 | top_k=3 | top_k=5 | 变化 |
|---|---|---|---|
| source_recall_at_k（文档级） | 0.7941 | **0.8627** | +0.069 |
| chunk_recall_at_1 | 0.6078 | 0.6471 | +0.039 |
| mrr_at_k | 0.4363 | 0.4456 | +0.009 |
| ndcg_at_k | 0.4791 | 0.4943 | +0.015 |
| refusal_accuracy | 0.9792 | 0.9583 | −0.021 |
| citation_source_match_rate | 0.4706 | **0.3725** | **−0.098** |
| 检索耗时 p50 / p95 | 450.6 / 918.0 ms | 418.1 / 737.7 ms | — |

按难度看文档召回的变化：

| 难度 | top_k=3 | top_k=5 |
|---|---|---|
| easy | 0.9167 | 0.9583 |
| paraphrase | 0.8667 | 0.9 |
| numeric | 0.8667 | 0.9 |
| **multi_source** | **0.3889** | **0.6111** |
| **multi_source 切片级** | **0.1111** | **0.1667** |

两点可以直接写进技术讨论的结论：

1. **多源题对检索深度最敏感**：只把 top_k 从 3 提到 5，多源文档召回就从 0.39 涨到 0.61（+57%）。
   这解释了为什么"再加一份文档"就能救活近一半的多源失败，也说明**多跳问题需要更大候选集**。
2. **候选变多不等于回答变好**：`citation_source_match_rate` 反而从 0.4706 掉到 0.3725，
   拒答准确率也略降。更多上下文会让生成端更难挑准要引用的段落。
   因此"提高 top_k"不是免费优化——**这正是重排序（Reranker）要解决的问题**：
   先扩大候选集保证召回，再用重排序把最相关的切片压到前面，而不是把上下文直接塞给模型。

`mrr_at_k` 基本不变（0.4363 → 0.4456）说明：多数题目第一名本来就对，top_k 的收益主要发生在
"第二名及以后"，也就是排序质量而非首条命中率——这与上面的解释一致。

### 结论三：生成端的引用与拒答

- 拒答准确率 0.9792（48 道期望拒答题中 47 道正确拒答）——拒答链路是可靠的；
- 但 `citation_source_match_rate` 只有 0.4706：**引用了正确文档 ≠ 引用了答案所在段落**，
  这是"回答有据"与"回答正确"之间最容易被夸大的一环；
- 勘误：第一次运行 18 道跨库隔离题实际有 15 道拒答、3 道未拒答；第二次有 14 道拒答。原描述把拒答与未拒答数量写反。人工核对表明多数不是模型幻觉，而是题目本身可被提问库的
  相邻主题资料部分回答（例如在 HR 库问"新人邮箱多久开通"，HR 库确实有《员工入职办理指南》）。
  这是**标注设计问题**，已在第 3 节加入了机械检测规则，并把唯一一处真实语义重叠（IT-55）显式标注。

## 6. 已知局限（不得省略）

1. 合成语料共 126 份 / 27.7 万字符，规模远小于真实企业知识库，结论不能外推；
2. `terms` 逐字匹配是切片级判定的代理指标，同义改写可能把"正确的切片"判为未命中；
3. nDCG 使用二值相关性，信息量弱于多级标注，**不衡量答案正确性**；
4. `keyword_pass_rate` 只是关键词筛查，**不是正确率**；报告里对应字段带 `heuristic_only` 后缀；
5. 未引入自动 LLM 裁判，答案正确性仍以 `report.md` 的人工复核列为准；
6. PDF 附录为 ASCII 正文，未验证中文 PDF 版式；
7. 检索指标只覆盖「BGE-M3 + Milvus 向量检索」这一条链路，重排序与混合检索尚未接入。

## 7. 幂等性复验（真实链路）

数据集之外，顺手在真实数据上复验了"重复投递不产生重复向量"这一关键性质：

```bash
# 对已 indexed 的版本 51 再次投递索引任务
POST /api/v1/document-versions/51/index   -> {"queued": true, "task_id": "af73bc76-..."}

# Milvus 实体数
重索引前: 768    重索引后: 768        # 未增加

# 该版本状态
{"version_id": 51, "status": "indexed", "chunks_indexed": 2, "error": null}
```

即重复投递被识别为已完成、不重复调用模型、不在 Milvus 产生重复实体。这是"幂等 upsert +
以 MySQL 作为状态来源"的直接证据，没有它就不该声称索引是幂等的。

## 8. 复现方式

```bash
conda activate knowops

python evals/tools/build_questions.py        # 校验标注 + 生成 questions.json / manifest.json
python evals/tools/build_pdfs.py             # 生成 PDF 附录
python scripts/check_dataset_pipeline.py     # 只验证入库与索引链路（不调用大模型）
python scripts/evaluate_v2.py                # 完整评估（检索 + 生成）
python -m pytest -q                          # 数据集回归校验
```

`evals/manifest.json` 记录了 126 份语料的逐文件 SHA-256 与题集哈希，可据此确认评估用的是哪一版数据。
